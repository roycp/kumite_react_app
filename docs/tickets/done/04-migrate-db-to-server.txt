## Context

db/database.web.ts is the single database abstraction used by all screens
and contexts (except AuthContext after ticket 03). It exports ~40 functions
across 13 collections. Each function currently reads/writes to AsyncStorage.

After this ticket, each function becomes a thin wrapper over an apiGet /
apiPost / apiPatch / apiDelete call. The file keeps the same exported
interface so no screens need changes.

Server endpoints used here (all from tickets 01 and existing routes):
  /api/users                      GET (with ?role=, ?email=), POST, PATCH /:id
  /api/registrations              GET (with ?userId=, ?tournamentId=), POST, PATCH /:id, DELETE /:id
  /api/martial-arts               GET, POST, PATCH /:id, DELETE /:id
  /api/rank-systems               GET (with ?martialArtId=), POST, PATCH /:id, DELETE /:id
  /api/organizations              GET, POST, PATCH /:id, DELETE /:id
  /api/tournament-templates       GET, POST, PATCH /:id, DELETE /:id
  /api/tournaments                GET, GET /:id, POST, PATCH /:id, DELETE /:id
  /api/user-martial-art-ranks     GET (with ?userId=), POST (upsert), DELETE /:id
  /api/coach-assignments          GET (with ?coachId=), POST, DELETE /:id
  /api/role-definitions           GET, POST, PATCH /:id, DELETE /:id
  /api/bracket-seeds/:tid         GET, PUT
  /api/weigh-in-results           GET (with ?tournamentId=), POST

### B. Users

export async function createUser(data): Promise<User>
  → apiPost<User>('/api/users', { ...data })
  Note: prefer using /api/auth/register from AuthContext. This function
  stays for any edge case (e.g., admin creating a user).

export async function getUserByEmail(email: string): Promise<User | null>
  → const users = await apiGet<User[]>(`/api/users?email=${encodeURIComponent(email)}`)
  → return users[0] ?? null
  Requires ticket 01's query-param support on GET /api/users.

export async function getUserById(id: string): Promise<User | null>
  → try { return await apiGet<User>(`/api/users/${id}`) }
  → catch { return null }

export async function getAllUsers(): Promise<User[]>
  → return apiGet<User[]>('/api/users')

export async function getAllAthletes(): Promise<User[]>
  → return apiGet<User[]>('/api/users?role=athlete')

export async function getUsersByIds(ids: string[]): Promise<User[]>
  → if (ids.length === 0) return []
  → const all = await apiGet<User[]>('/api/users')
  → return all.filter(u => ids.includes(u.id))
  (Simple approach — avoid N parallel requests for now)

export async function getRegistrationsByAthleteIds(ids: string[]): Promise<Registration[]>
  → if (ids.length === 0) return []
  → const all = await apiGet<Registration[]>('/api/registrations')
  → return all.filter(r => ids.includes(r.userId))

export async function updateUser(id: string, updates: Partial<User>): Promise<void>
  → await apiPatch(`/api/users/${id}`, updates)

### K. Coach / Manager Assignments

export async function assignAthleteToManager(managerId, athleteId): Promise<void>
  → try { await apiPost('/api/coach-assignments', { coachId: managerId, athleteId }) }
  → catch (err) { if (err instanceof ApiError && err.status === 409) return; throw err; }
  (409 = duplicate, silently ignore just like the old duplicate check)

export async function removeAthleteFromManager(managerId, athleteId): Promise<void>
  → const all = await apiGet<any[]>(`/api/coach-assignments?coachId=${managerId}`)
  → const match = all.find(a => a.athleteId === athleteId)
  → if (match) await apiDelete(`/api/coach-assignments/${match.id}`)

export async function getAthletesByManagerId(managerId: string): Promise<User[]>
  → const assignments = await apiGet<any[]>(`/api/coach-assignments?coachId=${managerId}`)
  → const ids = assignments.map(a => a.athleteId)
  → return getUsersByIds(ids)

Keep deprecated aliases (assignAthleteToCoach, etc.) pointing to the new functions.

## Comments
- database.native.ts (Realm) is NOT changed in this ticket — it is only
  used for native iOS/Android builds. A separate ticket can migrate it
  later if needed. For now the web/Expo build uses database.web.ts.
- The synced field returned by server functions is always set to true.
  If a caller checks `!item.synced` to queue a sync push, it will now
  always get false — which is correct since the server is the source of truth.
- Error propagation: all functions can now throw ApiError. Callers that
  previously never had errors should be wrapped in try/catch in the UI
  layer (screens) to show user-friendly messages. This is a follow-up
  concern; do not add error handling to database.web.ts functions themselves.
- ThemeContext.tsx uses localStorage.getItem/setItem('kumite-theme')
  directly — this is UI preference only and should NOT be migrated to
  the server. Leave it as-is.
- SyncUpScreen.tsx writes 'kumite_profile' to AsyncStorage — this is an
  onboarding helper that stands alone. Leave it as-is.
- After this ticket, the only AsyncStorage keys still in active use are:
    'session:jwt'       (managed by services/api.ts)
    'kumite-theme'      (managed by ThemeContext)
    'kumite_profile'    (managed by SyncUpScreen)
  All 'db:*' keys become dead storage that can be cleared on next app
  startup if desired.
